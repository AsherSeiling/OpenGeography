# SAGA `saga_cmd` as a separate program (T2 check, 2026-11-12)

Decision basis: DECISIONS "GPL tools as separate programs". Nothing GPL is linked or copied; GIS Studio starts `saga_cmd` and exchanges files with it.

## 1. Pinned source and build

- SAGA GIS **saga-9.5.1**, commit `00530d3630a5aa4d30d5e1219587db979daf8588` (github.com/saga-gis/saga-gis). Newest release tag at the time.
- `scripts/build-saga.sh` builds `saga_cmd` and the tool libraries with `-DWITH_GUI=OFF`, no source change, and stages `src-tauri/resources/saga/{saga_cmd, lib/, tools/, licenses/, SOURCE_OFFER.txt}`. `SAGA_SRC`, `SAGA_WORK`, `WX_PREFIX` allow offline and cached builds; the program is found through `GIS_STUDIO_SAGA` for tests.
- **Run time dependencies**: only wxWidgets *base* (a library with strings, files, XML; no GUI), linked **statically** (built from the pinned 3.3.4 release with `--disable-gui`). SAGA's CMake also asks for wx's `html` component, which is a GUI library its sources never use; the script gives the build a one-function stand-in archive in the build folder (SAGA stays untouched). Everything else is the system C++ runtime and OpenMP (libomp on macOS, libgomp on Linux, bundled next to it).
- **No GDAL, PROJ, PDAL, ODBC, curl or GUI**: the tool libraries that need them (io_gdal, io_pdal, io_webservices, db_odbc, garden_webservices, io_grid_image, statistics_kriging) are not staged. The script checks every staged binary and fails if it links anything outside the system and the staged libraries. Files go in and out as SAGA's native grids (`.sgrd` text header + `.sdat` raw cells) and shapefiles; GIS Studio writes and reads the grid format itself and applies the layer's CRS explicitly after the run (SAGA's own CRS dictionary, `share/saga/saga_prj.srs`, is not needed and not shipped; nothing is guessed from it).
- Size: 14 MB uncompressed for the 37 staged tool libraries (terrain, grid, shapes, TIN, table, statistics, climate, imagery tools, native I/O) plus saga_api and libomp. SAGA's CMake options switch off PDAL, GDAL, PROJ, OpenCV, ViGrA, Haru PDF, PostgreSQL and the Python bindings; the staged files were checked with `otool -L`: only `/usr/lib`, `/System` and our own `@rpath` libraries.

### Per platform, "no separate install"

| Platform | Status | How |
|---|---|---|
| macOS arm64 | **built and run** (2026-11-12): saga_cmd, saga_api, tools, libomp; rpaths rewritten to `@executable_path/lib` and `@loader_path/../lib`; links only `/usr/lib`, `/System` and the staged libraries | needs Xcode command line tools, cmake, Homebrew libomp at build time only |
| Linux x86_64 | written, **not run** | same script; wx base static; `patchelf` sets `$ORIGIN` rpaths; libgomp copied beside saga_api. Build on the oldest supported runner (same glibc floor as the app). Fits the existing AppImage private-libs flow |
| Windows x64 | written, **not run** | MSVC: `vcpkg install wxwidgets:x64-windows-static` (has the html component, no stand-in needed), `CMAKE_ARGS=-DCMAKE_TOOLCHAIN_FILE=…`; `saga_api.dll` beside `saga_cmd.exe`; OpenMP is MSVC's built-in (vcomp140.dll comes with the VC++ runtime the Tauri installer already requires). SAGA's own project builds Windows releases with the same recipe |

It qualifies for the 2026-11-04 rule on all three platforms in principle (no framework, no database, no Python, no MPI), but only macOS has been run. The Linux and Windows steps need one CI run each before a platform is marked verified.

## 2. Licence obligations

- **saga_cmd, most tool libraries: GPL-2.0-or-later. A few tool libraries (e.g. fill_minima, CliffMetrics, isocluster) are GPL-3.0-or-later**, so the staged set as a whole is distributed under GPL-3.0-or-later. **saga_api: LGPL-2.1-or-later.** No tool is non-commercial or has an extra restriction (grep of the source found none).
- **wxWidgets base** statically linked: wxWindows Licence (LGPL-2 plus an exception allowing binaries under the user's terms). **libomp**: Apache-2.0 with LLVM exceptions. **libgomp** (Linux): GPL-3 with the GCC Runtime Library Exception.
- Aggregation, not a combined work: GIS Studio (MIT OR Apache-2.0) only runs the program and exchanges files. Installers contain GPL programs (as DECISIONS already says); they must carry:
  1. the licence texts: staged by the script in `resources/saga/licenses/` (GPL-2, LGPL-2.1, wx licence, GPL-3 reference, LLVM OpenMP);
  2. the copyright notices: SAGA's tool sources keep them; `THIRD_PARTY_NOTICES.md` (generated by `scripts/third_party_notices.py`) gets a SAGA row;
  3. the source: the pinned tag and commit plus `scripts/build-saga.sh` (the same approach as WhiteboxTools), and a written offer: `resources/saga/SOURCE_OFFER.txt`, repeated in the README/About text. The release must publish the repository and the exact tag; if the repository is private at release, ship the source archive with the installer or attach it to the release;
  4. a row in `docs/OPEN_SOURCE.md` (added) and a line in the third-party notices script (to add with the first SAGA tool, when the shipped set changes);
  5. `scripts/license-gate.sh` checks linked libraries and stays as it is; its list of GPL-only names does not include `saga`, which is intentional: programs in `resources/saga/` are separate programs listed here, not libraries.
- The app must not load SAGA's libraries into its own process (no `dlopen`/linking of `libsaga_api`): it always runs `saga_cmd` as a child process.
- Methods, not code: tools' publications are cited per tool in `OPEN_SOURCE.md` when ToolSpecs are added.

## 3. Speed (macOS arm64, 8 cores, 4000 x 4000 Float32 synthetic DEM = 16 M cells, 10 m cells)

| Step | Time |
|---|---|
| SAGA import (GeoTIFF to .sgrd; in the shipped design GIS Studio writes the .sgrd itself, about the cost of a raw write) | 0.59 s |
| SAGA slope, aspect, curvature (tool 0, slope output, 9-parameter polynomial; staged hermetic build, `-f=s`: 0.83 s) | 1.14 s |
| SAGA export (.sgrd to GeoTIFF; shipped design: read the .sdat) | 0.77 s |
| **SAGA total with conversion** | **about 2.5 s** |
| WhiteboxTools slope (bundled v2.4.0, includes its own GeoTIFF read and write) | 2.26 s |
| SAGA analytical hillshade | 1.03 s |
| WhiteboxTools hillshade | 2.00 s |

SAGA is multi-threaded (OpenMP) and the sidecar process cost is negligible against the work: it is as fast as or faster than WhiteboxTools even counting two format conversions, so the "not much slower" test passes for grid terrain tools. Not measured: tools that are called many times on small inputs (those would be reimplemented, per the decision), and Linux/Windows speed.

## 4. Open points for the lead before ToolSpecs

1. Confirm the grid exchange design: engine writes the DEM as `.sgrd/.sdat` (Float32, explicit NoData, cell size, origin) and reads the outputs back, re-applying the input CRS. A small `saga.rs` (like `whitebox.rs`) with `saga_exe()` in `resources.rs`.
2. Which SAGA tools first (terrain morphometry, TPI, MRVBF/MRRTF, landform classification, wetness index, solar radiation, channel network and so on), and which overlap a WhiteboxTools tool already exposed (T1), so the Add menu does not offer two of the same.
3. Windows and Linux: one CI job each to build and run `scripts/build-saga.sh` before a platform is marked verified.
